## 2026-07-26 — session 1 (paper3 kickoff)

> We are trying to invent a new graph embedding algorithm for quantum annealing devices that ouperforms MinorMiner (MM) (https://github.com/dwavesystems/minorminer) on dense graphs as well as structured graphs.  The present repo contains Ember, a benchmarking repository and tool for evaluating embedding algorithms against different families of graphs (see https://arxiv.org/pdf/2604.25433 for a paper describing Ember).  Metrics of interest include performance/speed, average chain length (ACL), and, over N trials, mean ACL and variance in ACL.  We have some notes from a prior attempt in docs/paper2; and, on the new-algorithm branch, under docs/paper, there is another prior attempt.  Neither of these has worked great; the latest on the new-algorithm branch did some funny tricks with measurements that were unfair to MM, and the latest on this branch (factored) can beat MM on structured graphs but not on dense random graphs (which is arguably the more important case, since other specialized algorithms besides MM already exist for structured graphs - in practice, MM is just used as a fallback when no other special structure is identified).  Let's create a new branch - paper3, if you will - and start from scratch.  Let's synthesize every embedding algorithm paper we can find online, all details of MM (including with p-norm layout, which is how it's usually used per D-Wave documentation), and come up with at least 5 different distinct algorithm proposals that could potentiall outperform MM.  Some of these algorithms might be modifications of MM - for instance, MM has like three key components, we could consider replacing one or all of those with more high-performing algorithmic components.  Or we might invent algorithms that are entirely disjoint from MM.  Nonetheless, another metric we care about is viability - does the embedding algorithm compute a valid embedding for a given input problem graph.  MM's power comes from its rip-and-repair mechanism that iteratively works and works until it finds a valid embedding.  This explains why it is so successful at finding embeddings.  So we'd still like to preserve that quality in what we come up with, but surely there are smarter algorithms that naive rip and replace like what MM does.  Eventually, once we've brainstormed these algorithms and selected which ones we want to try and run with, we'll want to run all experiments on hyde06.dabh.io (accessible over ssh via hyde01.dabh.io as a jump host), which has lots of cores for parallelism, and we'll want to use a dynamic workflow that fans out subagents in order to try as many ideas as possible in parallel.

> Everything on hyde06 can be saved to /data/dabh/ where there should be ample TB of space free.  Don't use the /home directory if possible, that is what is almost full.

> I am not convinced that we want any best-of-K approaches - in my mind, it's unfair to compare a best-of-K approach with a single run of MM, since we could just run MM K times and take the best one as well, and we know that just doing that already produces a nice improvement.  Unless the proposed approach is SO fast that a best-of-K version is just as fast as one run of MM - that could be fair/interesting ("same time budget, two different algorithms race each other.").  Note that we should try to use all cores on hyde06.dabh.io that are available - I think it might just be 64 physical cores and 128 threads, so maybe only use up to 64 cores at once?  Just want to be sensitive about timing... if there are other processes running consuming CPU, or if we're strangling cores due to hyperthreading, that could lead to unfair performance numbers.
